# Persona Review — David, 45, Accessibility-Dependent User

I have low vision (I run everything at 200% zoom and rely on VoiceOver for anything dense) and a motor impairment that means I navigate entirely by keyboard. I've been in tech thirty years. I'm not asking for the moon — I'm asking for the WCAG 2.1 AA basics that browsers make easy to get right. I spent an hour with InstaSetter. Here's what I found.

## The single most important thing

**Add `:focus-visible` styles.** The `src/` tree contains zero focus-visible/focus-outline/focus-ring classes and the Tailwind config doesn't appear to re-enable them. This is a ten-minute fix in `globals.css`:

```css
*:focus-visible {
  outline: 2px solid #1a1a1a;
  outline-offset: 2px;
  border-radius: 4px;
}
```

Every other finding in this review assumes I can see where I am on the page. Right now I can't.

---

## The second most important thing

**Every icon-only button needs `aria-label`.** Code audit shows exactly one `aria-label` in the entire `src/` tree (a single "Close" in `prompt-reader.tsx`). The exploration log lists ten icon-only buttons in Flow Builder. For every one, my screen reader says "button" or reads the unicode character name. Ten minutes of adding `aria-label="Zoom in" / "Zoom out" / "Fit to screen" / "Toggle panel" / "Close" / "Add rule" / "Remove rule"` fixes this entirely.

## Patterns I'd roll out project-wide

1. **Shared `<IconButton>` component** that requires an `aria-label` prop via TypeScript — make the type `{ label: string; icon: ReactNode; onClick: ...; }` with no optional label. You cannot ship an unlabelled icon button if the types don't allow it.
2. **Linter rule**: turn on `jsx-a11y/button-has-type`, `jsx-a11y/no-noninteractive-element-interactions`, `jsx-a11y/label-has-associated-control`, `jsx-a11y/interactive-supports-focus` in ESLint. Your codebase already uses Next's ESLint config; flip the a11y plugin on and ship.
3. **Focus-trap utility** for the Simulator panel and View-prompt modal — use `focus-trap-react` or the native `<dialog>` element.
4. **Tab pattern**: the Flow / Runs / Variables / Versions / Bot tabs and the Design / Routing / Triggers / Data sub-tabs should use the WAI-ARIA Authoring Practices tab pattern (`role="tablist"`, `role="tab"`, `aria-selected`, arrow-key navigation).
5. **Canvas keyboard story**: write it down before you ship v1. "Users can navigate blocks with arrow keys, Enter to inspect, Delete to remove, Space to pick up and drop." Without this the Flow Builder fails Success Criterion 2.1.1 — a legal problem for any enterprise customer in the US, EU, or AU public sector.

## What worked

- Every interactive element is a real `<button>` or `<a>`, not a div with onClick. That means Tab and Enter work natively. Good bones.
- Home and 404 pages are simple, keyboard-reachable, and short. No landmark issues there because there's nothing to get lost in.
- The error boundary on `/dashboard/conversations` does render a "Try again" button, which is a real button with a real label. It just doesn't work.
- Colour palette is high-contrast on the home page (near-black text on cream) — easy to read at zoom.
- No autoplaying audio or video, no flashing content, no keyboard traps I encountered from the screenshots.

## What I'd ship first (2-week accessibility sprint)

1. Add `*:focus-visible` styles globally. (1 hour)
2. Add `aria-label` to every icon-only button in Flow Builder. (2 hours)
3. Wrap `<span aria-hidden="true">` around every decorative glyph on labelled buttons. (1 hour)
4. Fix the pointer-events-intercept bug on the tab bar — either it's a z-index mistake or an invisible overlay; it needs to go. (half a day)
5. Add a skip-to-main link and proper `<main>`, `<nav>`, `<aside>` landmarks. (half a day)
6. Associate every Inspector `<textarea>` with its section heading via `aria-labelledby`. (2 hours)
7. Convert the tab bar to the ARIA tab pattern. (half a day)
8. Add a real label to the Simulator input. (15 minutes)
9. Fix the Conversations error page so "Try again" actually retries and announces the result. (half a day)
10. Audit colour contrast on Flow Builder grey-on-cream text. (2 hours + design discussion)

That's under two weeks for one engineer. Most of these fixes are trivial additions. None of them require rethinking the product. The Flow Builder canvas keyboard story is a bigger piece of work and should be scheduled before v1 ships publicly — see `docs/flow-builder/PLAN.md` Week 7 rollout; today is the moment to fold a11y in, not after.
